# Design System Studio

งานทุกอย่างที่เกี่ยวกับ design system: สร้างระบบใหม่, เพิ่ม component, ปรับ token, ตรวจความสอดคล้อง
โหลด `design-taste-refs` ก่อนเสมอ (รสนิยม, กติกา Hallmark, วงจรตรวจงาน)

## โครงสร้างที่มีอยู่ (`~/Desktop/Design System/06-my-design-system/`)
- `core/` ใช้ร่วมทุกโปรเจกต์: `tokens-core.css`, `typography.md`, `spacing-radius-layout.md`, `motion.*`, `components/*.md`, `patterns/*.md`, `README.md` (ขั้นตอนสร้างโปรเจกต์ใหม่)
- `themes/<ชื่อ>/theme.css` สี ฟอนต์ เงา ของแต่ละโปรเจกต์ · มี `_template/` กับ `portfolio/`
- Token 3 ชั้น: primitive (อยู่ในธีมเท่านั้น) → semantic (ธีมกำหนด) → component (อยู่ใน core อ้าง semantic เท่านั้น)
- `preview/` หน้าตัวอย่าง · `scripts/bundle_preview.py` รวมไฟล์ให้เปิดเดี่ยวได้
- `decisions-log.md` บันทึกทุกการตัดสินใจ (เลขแถวต่อจากแถวล่าสุด)

## เริ่มระบบใหม่: ถามก่อนเสมอ
ใช้ AskUserQuestion ถามรอบเดียวไม่เกิน 4 ข้อ (ใส่ตัวเลือกแนะนำไว้แรก):

1. **เริ่มจากอะไร**
   - ใช้ core กลาง + ธีมใหม่ (แนะนำ: ได้ component ทั้งหมดทันที เปลี่ยนแค่สี ฟอนต์ มุม เงา)
   - แตกจากธีมที่มีอยู่ (ลิสต์ชื่อจาก `themes/` เช่น portfolio) แล้วปรับ
   - core ใหม่ทั้งหมด (เมื่อแพลตฟอร์มหรือความหนาแน่นต่างกันมาก เช่น dashboard หนาแน่น หรือแอปมือถือ native)
2. **Ref หลัก** ให้เลือกได้หลายอัน จาก `01-design-systems/`, `03-apps-we-love/`, `05-my-collection/INDEX.md` (อ่านรายชื่อจริงก่อนถาม อย่าเดา)
3. **บุคลิก** เช่น เรียบนิ่งแบบ shadcn / พรีเมียมแบบ Apple / สนุกมีสี / หนาแน่นแบบเครื่องมือทำงาน
4. **ใช้ที่ไหน** เว็บ, เว็บแอป, มือถือ และต้องมี dark mode ไหม

ถ้าเจ้าของไม่ตอบ หรือไม่ได้อยู่ ใช้ตัวเลือกแนะนำ แล้วเขียนไว้บนสุดของงานว่าเลือกอะไร
สีแบรนด์และฟอนต์ถามทีหลังได้ ระหว่างนั้นใช้ค่าจาก `_template`

## ขั้นตอนสร้าง (หลังได้คำตอบ)
1. คัดลอก `themes/_template/` เป็น `themes/<ชื่อ>/` ตาม `core/README.md`
2. ตั้ง primitive → semantic ให้ครบคู่สีพื้น/ตัวอักษร (`*-foreground`) ทั้ง light และ dark ตรวจ contrast ≥ 4.5:1 สำหรับตัวอักษร
3. ถ้าต้องมี component ใหม่: เขียน spec ใน `core/components/<ชื่อ>.md` (anatomy, ขนาด, 8 state, a11y, ข้อห้าม) แล้วค่อยเขียน CSS ที่อ้าง semantic token เท่านั้น
4. ทำหน้า preview แสดงทุก state ทั้ง light/dark แล้ว bundle: `python3 scripts/bundle_preview.py preview/<page>.html` (อาร์กิวเมนต์ที่ 2 คือไฟล์ปลายทาง **ห้ามใส่หลายหน้าในคำสั่งเดียว** รันทีละหน้า)
5. ทดสอบด้วย Playwright ที่ 320/375/768/1024/1280 light + dark: ไม่มี scroll แนวนอน, ปุ่มไม่ตัดสองบรรทัด, focus เห็นชัด
6. วงจรตรวจงานจาก `design-taste-refs`
7. เพิ่มแถวใน `decisions-log.md` อัปเดต `README.md` ของระบบ

## ตรวจระบบที่มีอยู่ (audit)
- หา hex, px ลอย, font-family ที่ไม่ผ่าน token: `grep -n "#[0-9a-fA-F]\{3,6\}\|border-radius:[0-9]\+px\|font-size:[0-9]\+px"`
- เทียบ component กับ spec ใน `core/components/` ว่า state ครบไหม
- รายงานเป็นตาราง: ปัญหา / ระดับ / วิธีแก้ แล้วแก้ทีละกลุ่ม

## วิธีทำงานกับไฟล์
- แก้บนเครื่องเจ้าของผ่าน device bash หรือ stage มาที่ workspace เพื่อรัน Playwright แล้ว commit กลับ
- แก้ด้วยสคริปต์ Python ที่ assert ว่าข้อความเดิมเจอครั้งเดียวก่อนแทนที่ สำรองไฟล์ก่อนแก้
- ห้ามลบไฟล์ของเจ้าของถ้าไม่ได้ขอ

## ความรู้กลางที่ใช้ได้ทุกโปรเจกต์ (สะสมจากงาน Migma ถึง 13 ต.ค. 2026)

ข้อด้านล่างเป็น pattern ที่เจ้าของเคาะแล้วหรือเป็นบั๊กที่เจอจริง ใช้เป็นค่าเริ่มของทุกระบบใหม่ ส่วนเรื่องที่เฉพาะกับพอร์ตอยู่ในสกิล `portfolio-maker`

### ฟอร์มและการตรวจข้อมูล
- label อยู่เหนือช่องเสมอ placeholder คือตัวอย่างข้อมูลจริง ไม่ใช่คำสั่ง · ช่องที่ตัวอย่างจะอ่านเหมือนค่าที่กรอกแล้ว (เช่น ชื่อคน) ไม่ใส่ placeholder ให้ย้ายคำไปไว้ใต้ช่อง
- ดักที่หน้าบ้านทุกอย่างที่ดักได้ และบอกจุดที่ผิดให้ตรง เช่น “ยังไม่มี @”, “เบอร์ยังไม่ครบ ตอนนี้มี 4 หลัก” ไม่ใช้ข้อความรวมแบบ “กรอกไม่ถูกต้อง”
- แยกสองระดับ: รูปแบบผิดแน่ = กันบันทึก · ระบบเดา (เช่น โดเมนพิมพ์พลาด) = คำเตือน ยังบันทึกได้
- ช่องที่เลือกประเภทแล้วแต่ยังว่าง ต้องมีคำเตือน แต่ไม่ขึ้นกับแถวที่เพิ่งสร้างจนกว่าผู้ใช้จะออกจากช่อง
- ผู้ใช้กรอกผิดช่องแบบที่เดาได้ (วางลิงก์ลงช่องชื่อ) ให้ระบบย้ายให้แล้วแจ้ง ไม่ใช่ขึ้น error
- รับข้อมูลแบบที่คนไทยกรอกจริง: ปี พ.ศ. แปลงให้ เบอร์โทรรับช่องว่างและ +66 และป้ายต้องบอกว่ารับได้
- ช่องที่มีค่าที่ใช้บ่อย เป็นทั้งช่องพิมพ์และรายการเลือกในช่องเดียว
- คำถามหลายตัวเลือก: ไม่ติ๊กคำตอบไว้ก่อน ขึ้น “เลือก 1 ข้อ” ใต้ข้อที่ยังไม่ตอบ และ “อื่นๆ” ต้องมีช่องพิมพ์เอง
- รายการแนะนำต้องตามบริบทของผู้ใช้ (สายงาน ภาษาที่กำลังพิมพ์) คำที่ไม่มีคู่ในภาษานั้นไม่ต้องขึ้น

### การลบ การยืนยัน และคำที่ใช้
- ของชิ้นเล็กที่ย้อนได้: ทำทันที + toast “เลิกทำ”
- ของที่เนื้อหาเยอะ กระทบคนนอก หรือย้อนไม่ได้: หน้าต่างยืนยัน บอกสิ่งที่จะหาย ปุ่มเป็นคำกริยาของการกระทำ โฟกัสเริ่มที่ยกเลิก
- คำเดียวทั้งระบบ: “เลิกทำ” สำหรับย้อน · “ยกเลิก” ในหน้าต่างยืนยัน · “ปิด” ในหน้าต่างข้อมูล
- ปุ่มที่ทำงานเสร็จแล้วต้องไม่กลายเป็นปุ่มเทากดไม่ได้ ถ้ายังมีสิ่งที่ผู้ใช้อยากกลับมาทำ (เช่น เผยแพร่แล้ว → แชร์ลิงก์)

### การนำทางและการเริ่มใช้งาน
- จังหวะแรกหลังเข้าแอป ให้มีสิ่งเดียวบนจอ อย่าให้ทัวร์ toast และแถบขั้นตอนขึ้นพร้อมกัน
- ตัวบอกความคืบหน้าต้องอยู่ทุกหน้ารวมหน้าย่อย และไม่เลื่อนหายไปกับเนื้อหา (เกาะบนและย่อตัวตอนเลื่อน)
- ขั้นที่ไม่บังคับ ให้ข้ามได้ด้วยปุ่มที่เห็นชัด และแสดงสถานะ “ข้าม” ต่างจาก “เสร็จ”
- ของที่ระบบยังไม่รองรับ เอาออกจากหน้าจอ ดีกว่าโชว์แล้วใช้ไม่ได้
- การตั้งค่าที่คนมองหาบ่อย (เช่น ภาษา ขนาดตัวหนังสือ) ต้องอยู่ในที่ที่เห็นตลอด ไม่ซ่อนลึกในแท็บตั้งค่า
- ฟีเจอร์ AI ต้องอยู่ในตัว บอกก่อนกดว่าจะทำอะไร ใช้เครดิตไหม และเลิกทำได้ ห้ามให้ผู้ใช้คัดลอกไปวางในแอป AI อื่น

### Responsive และ CSS ที่พลาดบ่อย
- วัดที่ 320 / 360 / 375 / 414 / 768 / 1024 / 1280 และต้องวัดสถานะที่ข้อความยาวที่สุดด้วย (เช่น ปุ่มตอนมีงานยังไม่บันทึก) ไม่ใช่แค่สถานะปกติ
- `[hidden]` แพ้ `display` ของคลาสเสมอ ทุก element ที่มีคลาสกำหนด display และใช้ `hidden` ต้องมีกติกา `[hidden]{display:none}`
- ชิ้นส่วนซ่อนสำหรับโปรแกรมอ่านจอ (`.vh`, live region) ที่วางท้าย body ต้อง `position:fixed` ไม่งั้นดันให้ทั้งหน้าเลื่อนได้ 1px และแถบบนหลุด
- แอปแบบเต็มจอบนจอคอม ให้ `html,body{overflow:hidden}` แล้วเลื่อนเฉพาะในแผง
- แถบเครื่องมือที่ของเยอะ: กำหนดลำดับการย่อไว้ล่วงหน้า (ซ่อนข้อความเหลือไอคอนก่อน แล้วค่อยซ่อนตัวเลข) และปุ่มไอคอนล้วนต้องมีชื่อให้โปรแกรมอ่านจอ
- พื้นที่กด 44px ทำด้วย `::before` ได้ ตัวปุ่มเล็กกว่านั้นได้
- โหมดตัวหนังสือใหญ่: ตั้ง token ข้อความเล็กทุกตัวให้ไม่ต่ำกว่า 16px ไม่ใช่ขยายเฉพาะเนื้อหาหลัก
- หน้าต่างที่ยาวเกินจอ แบ่ง 2 คอลัมน์บนจอคอม คอลัมน์เดียวบนมือถือ

### สองภาษา
- อย่าผูกโค้ดกับภาษาใดภาษาหนึ่ง (`lang==='en'`) ให้มีแนวคิด “ภาษาหลักที่กรอกก่อน” กับ “ภาษาที่สอง” ผู้ใช้เป็นคนเลือกว่าภาษาไหนมาก่อน
- สลับภาษาแล้วต้องไม่มีคำของระบบค้างเป็นอีกภาษา ตรวจด้วยสคริปต์เก็บข้อความทุกหน้า รวม placeholder, aria-label และข้อความใน CSS `content`
- ปุ่มสลับภาษาแสดงภาษาปัจจุบัน ไม่ใช่ภาษาปลายทาง

### ข้อยกเว้นจาก token ที่ยอมรับ
- QR: ดำบนขาวคงที่ทุกโหมด เพราะกล้องต้องการคอนทราสต์ · โลโก้ของบริการอื่น (เช่น Google) ใช้สีจริงของเขา · เอกสารสำหรับพิมพ์มีชุดสีเทาของตัวเอง
- ขนาดไอคอนควรเป็น token (ตอนนี้ยังเขียนเป็นตัวเลขตรงๆ 14–24px ในงาน Migma ควรเก็บเข้า core)

### เอกลักษณ์ของแบรนด์ในชิ้นเล็ก
- ให้ของที่ระบบสร้าง (QR, เอกสาร, ภาพแชร์) ยืมรูปทรงและสีจากโลโก้ แทนการวางโลโก้ทับ เช่น QR ที่ใจกลางตาเป็นสีแบรนด์และมีจุด accent หนึ่งจุด
- มีกันสีที่ผู้ใช้เลือกเอง: ถ้าสีอ่อนเกินจนของนั้นใช้งานไม่ได้ ให้กลับไปใช้สีตั้งต้น

### ความซื่อตรงและการทดสอบ
- ต้นแบบที่ให้คนลอง: ของจำลองต้องติดป้าย ไม่แต่งตัวเลขหรือผลลัพธ์ปลอมลงในข้อมูลผู้ใช้ ถ้าทำไม่ได้ให้ปล่อยว่างและบอกตรงๆ
- ก่อนส่งต่อไปทำระบบจริง: เอาป้ายต้นแบบ ปุ่มทดสอบ และข้อมูลจำลองออกจากหน้าจอ เก็บทางลัดของนักพัฒนาไว้หลังสวิตช์ (`?dev=1`) และจดรายการจุดที่ยังเป็นของจำลองไว้ในบันทึกการเปลี่ยนแปลง
- ทดสอบในเบราว์เซอร์จริงทุกครั้ง: ฆ่าเบราว์เซอร์ทดสอบตัวเก่าก่อนรัน รอโหลดให้นานพอ และ headless ไม่ยิง `focusout` ให้ ต้องยิงเอง
- มีสคริปต์ไล่ตรวจทั้งระบบ: หน้าเลื่อนแนวนอน ชิ้นที่ล้นจอ ปุ่มตัดสองบรรทัด ข้อความโดนตัด แล้วเปิดดูภาพจริงอย่างน้อยหนึ่งภาพต่อรอบ
- รายงานต้องแยก “ตรวจแล้ว” กับ “ยังไม่ได้ตรวจ” บอกที่มาของดีไซน์แต่ละจุด และบอกตรงๆ เมื่อไม่มีเรฟ
